# Self-iteration Audit：使用期自迭代审计（self_iteration_audit）

辞达交付后，使用者的真实发布产出是最后的校准语料。本工作流把"定期用已发布文章
审计辞达自身"固化为标准动作，对应项目任务书 §7"Corpus corrects Theory"与
强制补丁 §14"分析完成后立即更新知识库"、§28"修一个问题制造另一个问题的回归防线"。

触发方式：用户要求"评估辞达 / 自迭代 / 审计近期文章"，或积累了约 5–10 篇
新的已发布内容时主动建议执行一次。

## 0. 输入

- 近期已发布文章集合（用户指定目录或逐篇提供），标注平台与发布日期；
- 可选：读者反馈、数据表现（只作参考，不作质量裁定）；
- 可选：用户对每篇的满意度标记（满意 / 一般 / 翻车）。

## 1. 单篇诊断

对每篇按 `diagnose_text.md` 十二项诊断过一遍，重点记录：

- 命中的既有反模式（附文本证据）；
- 疑似新反模式（既有库无法归类的复发问题）；
- 既有机制的滥用或失效（如修辞峰值被实例化为固定形式）。

单篇结论允许"此篇无需大改"，不为凑工作量虚报问题。

## 2. 跨篇审计（本工作流的核心增量）

把文章按时间排开，提取并比对：

```yaml
opening_types:        # 各篇开头类型分布
skeletons:            # 各篇骨架分布
section_title_forms:  # 首节/各节标题的句式签名
closing_moves:        # 收尾动作分布（提问 CTA / 综合判断 / 行动邀请……）
emphasis_forms:       # 强化形式分布（加粗对仗句 / 独立成段格言 / 排比……）
register:             # 语域分布；是否存在用户未声明的多套声音
```

判定标准：

- 任一维度上超过半数文章同款 → 命中 `account_level_monotony`，记录为 P0 修复对象；
- 同一强化形式在 3 篇以上复现 → 记入 `gold_quote_inflation` 的形式签名预算；
- 发现的两篇文章骨架逐节对应 → 单独摘录对比，作为机制修订的证据。

## 3. 归因：是 skill 的问题，还是任务的问题

每条发现必须归因后再动手：

- **skill 缺陷**：机制缺失、反模式库未覆盖、平台文件缺位（如主战场平台没有目录）、
  契约步骤漏执行 → 进入第 4 步修订；
- **执行漏步**：skill 已有明确要求但该批文章未体现（如候选比较被跳过）→
  在主流程或自检中加强提醒，不新增规则；
- **用户偏好**：复发模式经确认是用户有意选择 → 记入 Personal Style Profile 的
  偏好层，不进通用方法论（对应任务书 §6 Practitioner Hypothesis 原则）；
- **素材上限**：问题源于素材而非表达 → 只记录，不改 skill。

## 4. 修订知识库

按归因结果执行：

- 新反模式：按 `name / symptom / example / why_it_hurts / possible_mechanism / repair /
  exceptions` schema 新建文件，实例优先取自本次真实产出（摘录公开内容时注意授权）；
- 机制修订：补充 boundary_conditions 或 overuse_risk，不推倒重来；
- 平台文件：缺失则新建；已有则把审计发现的入口/形态事实写入；
- SKILL.md：只登记路由与自检项变化，不堆细节。

每次修订写明证据来源（哪几篇文章、什么模式），保持 provenance 原则。

## 5. 回归验证（防止修一个制造一个）

修订完成后，在工程仓库（含 `evals/`、`scripts/` 的完整 checkout）执行：

```bash
python3 scripts/build_mechanism_graph.py   # 重建机制图谱，确认无悬空关联
python3 scripts/run_regression.py          # 规则回归
python3 scripts/run_evals.py               # benchmark 评测（如环境允许）
```

- 回归失败先修回归，再交付修订；
- 修订涉及既有机制的行为变化时，用 `compare_versions.py` 对照新旧产出，
  确认原意、结构与平台适配没有退化；
- 工程仓库不可用时（如只有安装包环境）：至少完成机制图谱重建与人工抽查
  3 个历史任务的假想重跑，并把跳过的回归明确记录在交付说明里。

## 6. 交付审计报告

报告包含：

1. 样本清单与平台分布；
2. 单篇诊断摘要（允许"无需大改"）；
3. 跨篇模式表与命中证据；
4. 归因分类（skill 缺陷 / 执行漏步 / 用户偏好 / 素材上限）；
5. 已执行的修订清单（文件级）与回归结果；
6. 遗留问题与下一轮审计的建议时机。

## 边界

- 审计产出的是**修订与证据**，不是"AI 味评分"或传播效果承诺；
- 已发布文章不返工改写（账号级修复靠迭代，不靠改写历史）；
- 审计频率不高于产出积累速度；每次审计必须有至少一条可归因发现才启动修订，
  没有问题的审计是合法结果。
