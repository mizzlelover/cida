# 知乎回答与文章（zhihu）

知乎任务先承担“回答义务”：读者应知道文本如何回答了问题，再评价证据、解释和判断是否有增量。
不要把高密度理解成堆资料，也不要把有判断理解成为反对而反对。

## 1. 先对准问题与内容形态

```yaml
surface: answer / article
entry_route: question / search / recommend / follow / unknown
question_literal: 问题字面在问什么
question_real: 为作出判断或行动，真正还需要解决什么
```

- `answer`：开头先给回答方向或核心答案；若需重框，先承认原问题，再说明为什么换观察单位。
- `article`：标题和首段自行建立问题，不假装在回答一个不存在的问题。
- 搜索或问题入口可减少泛泛背景；推荐或关注入口仍需让陌生读者理解问题为何值得看。

记录读者知识水平、可能反方和作者证据位置。没有证据支持强判断时，降低确信度或补证据，
不通过“知乎风格”强行提高判断力度。

## 2. 原生基线

```yaml
logical_explicitness: 7–10
information_density: 6–9
rhetorical_density: 2–6
judgment_strength: 由证据与回答任务决定
evidence: 底线；数据、出处、经验和推断分别标明
reader_interaction: 以真实反驳和疑问为主
```

个人经验可以作为证据，但要交代经验范围；专业知识可以简化语言，不能省略关键推理桥。

## 3. 候选结构

- **直接回答—关键理由—证据—反方—边界**：适合明确问题与有依据的判断。
- **概念澄清—问题重框—机制解释—回到原问题**：适合问题含有错误预设或概念混用；
  重框后必须实际回答，不能只展示“我看问题更高级”。
- **经验案例—可迁移机制—反例或限制—回答**：适合作者确有相关经验；
  个人故事不能自动证明普遍规律。
- **共同标准—方案比较—条件化结论**：适合“选哪个”“值不值”等决策问题。

至少比较“直接回答”与另一种可能更有增量的结构，选择最能服务问题的一版。

## 4. 价值兑现

- 第一内容单元给答案方向、核心结论或必要澄清，不让读者先读漫长资历和情绪；
- 前段给一个最关键理由、证据或有解释力的框架；
- 中段处理推理桥、反例、反方与适用条件，每一节都仍在回答问题；
- 结尾收束为对原问题的可用回答，必要时给行动或判断标准，不重复全部论据。

## 5. 验收

- 把答案单独摘出来，能否看出它回答了什么？
- 每个关键论断的依据来自事实、出处、经验还是推断，是否混淆？
- 是否回应最强反方，而非挑一个容易击败的稻草人？
- 重框、故事和抖机灵是否实际帮助回答？没有就删除或降级。
- 长度是否来自问题复杂度，而不是“长显得专业”？

## 反平台腔

警惕“谢邀”残留、资历表演、“人在美国刚下飞机”式包装、为反对而反对、
伪引用、堆名词和把个人经历冒充普遍规律。专业感来自把问题真正解决，不来自姿态。
