# 视频口播与视听脚本（video_script）

视频脚本按时间和视听单位被消费，不是书面文章的朗读版。`video_script` 只描述内容形态；
必须在任务契约中另记实际发布平台、入口、受众关系、视频形式与目标时长。未知时不猜平台算法。

## 1. 任务契约

```yaml
platform: 实际发布平台
surface: talking_head / voiceover / demo / interview_clip / live_script
entry_route: search / recommend / follow / share / unknown
duration: 用户目标时长；未知则按内容估计并说明
visual_assets: 已有或可真实制作的画面、演示、截图、图表、场景
```

- `search`：尽快对准具体问题，先给解决方向，再演示或解释；
- `recommend`：用具体矛盾、结果、动作或现场建立相关性，不用无关吼叫和夸张表情文案；
- `follow`：可承接共同背景，但单条仍要让普通关注者理解；
- 没有视觉资产时写可独立成立的口播，不虚构“大家看这个”后面的东西。

## 2. 原生基线

```yaml
orality: 8–9
sentence_length: 以自然一口气为参考，按表达者实际朗读调整
pronounceability: 强制检查
listener_memory: 关键判断、必要重复与阶段回检
signposting: 在听觉转向处显性，在显然处克制
visual_audio: 画面负责展示，口述负责解释、判断与连接
```

避免连续长定语、嵌套句和绕口组合。数字与专有名词第一次出现要清楚；
复杂数字只有在不改变精度时才换成可感类比。

## 3. 候选结构

- **结果或演示—方法—条件**：先展示真实结果/问题 → 给关键步骤 → 说明适用条件。
- **具体矛盾—尝试或证据—发现—行动**：从观众熟悉的困境进入，用过程产生理解变化。
- **问题—关键解释—证据/演示—回答**：适合知识解释，开头的问题必须真的被回答。
- **场景故事—变化—机制—回到观众**：适合有真实事件和转折的材料，不用虚假故事撑钩子。

至少比较两种信息顺序。候选差异要落在观众何时看到证据、何时获得答案，不只是换第一句。

## 4. 分时段价值兑现

成稿前内部列出 `beat / viewer_gain / spoken / visual`：

| 时段 | 观众获得 | 口播任务 | 画面任务 |
|---|---|---|---|
| 开场 | 知道对象、相关问题与可期待价值 | 建立相关性并给真实约定 | 立即展示相关对象、动作或结果 |
| 前段 | 第一次有用获得 | 给关键判断、第一步或证据 | 证明或展示，而非只换背景 |
| 中段 | 新解释、新步骤、新证据或变化 | 推进，不同义重复 | 与当前信息同步，必要时留气口 |
| 结尾 | 完成判断、方法或行动 | 收束，干脆结束 | 支持最终结果或行动 |

这只是检查框架，不是固定四段模板。时长越短越要集中一个主要兑现；
长视频按意义单元设置回检与重新进入点。续读来自已兑现价值和尚待解决的真实任务，
不靠“最后有惊喜”却迟迟不给内容。

## 5. 交付与朗读验收

- 用户需要拍摄脚本时，交付“时间/口播/画面或动作/本段兑现”表；
  只需要口播时给干净稿，画面提示另列，不混入朗读正文；
- 默读或实际朗读一遍：喘不上气、拗口、听觉指代不清的地方重写；
- 每个“这个、那个、刚才”在纯听觉中是否指得清？
- 画面是否真的存在并能证明/展示当前内容？声画是否各说各话？
- 前段是否已有兑现，中段是否持续推进，结尾是否不拖长尾和多重 CTA？

## 边界

不写“呃、那个”伪造自然，不把逐字聊天稿当口播稿，不把文章分段朗读当视频适配。
不编造演示结果、画面材料或平台效果。
