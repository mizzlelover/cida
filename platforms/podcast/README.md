# 播客稿与听觉章节设计（podcast）

播客是长程听觉跟随：听众可能伴随性收听、短暂掉队再回来。任务是维持一条可重入的
话题与价值主线，不是把松散当自然，也不是机械地每隔固定分钟总结。

## 1. 任务契约

```yaml
platform: 实际发布平台或分发场景
surface: solo / co_host / interview / narrative
entry_route: follow / search / recommend / share / unknown
duration: 目标单集时长
preparedness: outline / semi_prepared / full_script
participant_roles: 主持、嘉宾、共同主持各自的知识与追问职责
```

- `follow`：可利用节目共同背景，但开场仍说明本集独立问题与价值；
- `search/share`：标题、 shownotes（如需要）和开场让新听众知道主题、问题与适用范围；
- `recommend/unknown`：不猜算法，用可独立理解的单集约定减少进入成本；
- 访谈先判断嘉宾真正能提供什么，不把主持人想要的长篇观点塞给嘉宾作陪衬。

## 2. 原生基线

```yaml
orality: 7–9
information_density: 成串推进，串与串之间留气口
listener_memory: 关键词、阶段收拢与话题回环
signposting: 转场、回入与角色分工清楚
preparedness: 按任务选择，不伪装即兴
```

`recap` 按章节、认知节点和听众可能掉队的位置设置，不执行“每 10–15 分钟必须 30 秒”配额。
重复只保留能帮助听觉记忆的内容，避免文章式重复总结。

## 3. 候选结构

- **核心问题—分段探索—综合回答**：适合知识解释与观点讨论，每段解决一个子问题；
- **真实事件—追问与发现—机制—回看**：适合叙事和人物材料，事件必须带来理解变化；
- **观点对照—证据追问—分歧澄清—暂时结论**：适合对话与访谈，保留真实分歧，不强行共识；
- **听众问题—经验/证据—可执行建议—边界**：适合实用型单集。

比较候选时同时看单集价值与嘉宾/材料是否撑得住，不为了戏剧性设计没有依据的冲突。

## 4. 单集价值路线

- **开场**：说明本集问题、与听众的关系和可期待获得；可用真实冷开场，但尽快给方向；
- **前段**：先解决一个子问题、给一个有解释力的故事或证据，避免长寒暄与履历堆叠；
- **章节**：每章有不同认知任务；支线出口回到主线，关键处给简短定位；
- **重入点**：在复杂转换后说明“现在讨论的是什么”，不反复向一直在线的听众道歉式总结；
- **结尾**：形成暂时结论、行动、未解问题或观点回返，不把所有内容重播一次。

## 5. 话轮与交付

- 独白稿可写完整口播；对话稿优先写问题梯、分工、证据点和可能追问，不把双方每句反应都演好；
- 访谈问题一次只承担一个主要任务，给嘉宾真实回答空间；准备事实追问与离题回接；
- 保留有功能的自我修正和追问，删除纯填充；不为了“像播客”写假笑、假打断和假即兴；
- 用户需要时再交付章节标题、时间轴与 shownotes，不与逐字稿混成一团。

## 6. 验收

随机从中段一个章节进入，能否迅速知道当前话题及与主问题的关系？
每个支线是否有出口，每个章节是否有新增值，开场约定是否在结尾得到回应？
对话是否来自角色真实知识与分歧，而不是主持人替所有人发言？

## 边界

Podcast Rambling 是失败模式：自然松散只在表层，底层话题结构必须成立。
相关机制见 `knowledge/mechanisms/topic_progression.md`、`topic_return.md`、`turn_projection.md`。
